# API

The table below lists the main paths under `/api/v1` and `/assistant-api/v1`; the full specification is in the OpenAPI (`/v3/api-docs`) of the running backend; the backend ships no interface for trying calls, so feed the specification to your own tool (Postman, Insomnia or a code generator).
Every response is wrapped in `ApiResponse`, and errors carry a stable `errorCode`.
The script `e2e/api/check_docs.py` checks that the Core paths in the table are in the OpenAPI.

| Path | What it does |
|---|---|
| `POST /api/v1/models/plan`, `/apply` | Preview and apply a model file (ADMIN); the plan has `impacts`: for each new action that requires an added field with `require`, the number of records in the source status that still lack that field, and `CHANGE_ACTIONS` names the action that changed |
| `POST /api/v1/models/merge` | Merge a file that has `extends` with a template of the library and return the complete file for preview, without saving; `plan` and `apply` merge the same way (ADMIN) |
| `POST /api/v1/models/upgrade` | Run the migrations in sequence up to the current format and return the content for preview, without saving the file (ADMIN) |
| `POST /api/v1/models/{model}/rollback/plan`, `/rollback` | Preview and go back to the previous version (ADMIN) |
| `POST /api/v1/models/{model}/resume`, `/abandon` | Finish or abandon an apply that stopped halfway (ADMIN) |
| `GET /api/v1/models`, `/models/{model}/runs` | The models that were applied and the history of each step (ADMIN); each model has `leftOut` (true when the saved version does not pass the checks of this release so the model does not run), `problems` (the reasons) and `warnings` (the part of the model that runs after being dropped because of a rule that was tightened) |
| `GET /api/v1/models/schema`, `/families`, `/templates`, `/{model}/versions` | The specification of the model file, the workflow families with their statuses and actions, the template library and the applied versions, for the control panel (ADMIN) |
| `GET /api/v1/models/{model}/data-lineage` | The lineage of each field of a running model, built at call time from the model itself, with the running version: `origins` (the roles that may write, the default, the referenced entity, the unit, the file, the code generated when the record is created, the old name), `uses` (the rules that read the field: `required_when`, `require` and `when` of an action, the owner, the unit scope) and `destinations` (history, event stream, webhook, archive); there is no transformation step because the core keeps the value as it is (ADMIN) |
| `GET /api/v1/models/{model}/data-catalog` | The data catalog of a running model, built at call time from the model itself: where data comes in (roles and registered outside applications), where it goes out (webhooks, completion actions, the event stream, the archive), the reference and owner links between entities, and for each entity the record count, the permissions by role and the list of fields (ADMIN) |
| `POST /api/v1/models/diagram` | The workflow diagram of a model file: statuses, actions (with their own role and required fields), the handling role, the deadline, the escalation levels, the automatic closing action and the `after` actions; a wrong file gives `valid: false` with the line and column (ADMIN) |
| `GET /api/v1/meta/models` | The metadata the caller may see, with `modelVersion` and the `aiTasks` of an entity when declared; a held model shows with `held`, `modelVersion=null` and no entities; each field also has `multiple`, `min`, `max`, `pattern` and `requiredWhen` (`{field, op, value}`) when the model file declares them, and each entity has `ui` (`icon`, `menu`, `list`, `form`, `hints`) when declared; `process.effects.asynchronous=true` means the effect was only put into the outbox and its completion is not yet confirmed outside |
| `GET /api/v1/meta/models/{model}/openapi` | The OpenAPI document of a running model, generated at call time from the model itself so it changes with every apply and rollback: the paths of the data API for each entity the caller may reach (an ADMIN sees all), the fields with type, required and choices, the actions of the workflow, the error codes; it returns the document itself, without the `ApiResponse` wrapper, so a client generator or an API tool can read it from this address; 404 when the model does not exist or the caller reaches no entity |
| `/api/v1/data/{model}/{entity}` | List, create, view, edit, delete; filter with `filter.<field>[.<operator>]` (a `boolean` field compares only for equality, a `date` field compares for equality and `gte`, `lte`, a multiple-choice field accepts only `contains`), `q` is the words to look for: every word must be present, ignoring case and accents, in at least one `text`, `code` or single-choice `choice` field of the entity (up to 8 words and 200 characters, error 400 when the entity has no such field; it matches only text normalized to NFC; a query with `q` is cut after 10 seconds), `sort`, `order`, `page`, `size`; a `boolean` value is `true` or `false`, a `date` is `YYYY-MM-DD`, a multiple-choice field is an array of strings; an edit takes the `version` and `modelVersion` that were read, and a record that has changed gives 409 `ERR_CONCURRENT_MODIFICATION` even when the value does not change; a model that has changed gives 409 with `data.reason=MODEL_VERSION_CHANGED`; 403 `ERR_ACTION_NOT_ALLOWED` and 409 `ERR_INVALID_STATE` have `data.reason`; creating a record and actions accept the header `Idempotency-Key` (1 to 128 characters of `A-Za-z0-9._:-`): sending the same key with the same content again returns the answer of the first time with the header `Idempotent-Replayed: true` and does not do it again, the same key with a different request (different content or target) is 409 with `data.reason` `IDEMPOTENCY_KEY_REUSED`, a malformed key is 400, and a refused request does not keep its key; a key belongs to the sender and is kept for 24 hours; the returned record carries `webUrl`, the page of the record in the web interface (see [Extension points](./EXTENSIONS_EN.md#links-to-the-dx-os-web-interface)), which is absent when you run `dxos start --core` |
| `GET /api/v1/data/{model}/{entity}/stats` | Counts over the rows the caller may see, taking the same `filter.*` filters and `q` as the list: `total`; for an entity with a workflow also `byStatus` (the number of records in each status) and `overdue` (records whose deadline is before `computedAt`), `avgDecisionSeconds` (the average seconds from creation to the final status), `avgOpenAgeSeconds` and `oldestOpenAgeSeconds` (the average and the largest age of records not yet in a final status, up to `computedAt`; these three are `null` when no record can be counted), and `timeInStatus` (an array of `status`, `visits`, `avgSeconds`, `maxSeconds`, sorted by average descending and then by status code ascending, empty when there are no visits); each re-entry counts on its own, an open visit counts up to `computedAt`, and the last visit of a closed record is left out; for an entity that declares a deadline also `closedOnTime` and `closedLate`, the number of closed records (not counting withdrawn ones) that were never overdue and that were overdue at some time, counted from the `overdue` history rows; a record that was overdue and then finished in time at a new deadline still counts as having been overdue; for an entity with a `unit` field also `byUnit`; the query is cut after 10 seconds |
| `GET /api/v1/data/{model}/{entity}/report` | Group the rows the caller may see by a field and compute figures, taking the same `filter.*` filters and `q` as the list. `groupBy` is a choice, unit or boolean field (not a multiple-value field), `status` for an entity with a workflow, or a date field and `created_at` by month in the form `field:month` (the month is computed in UTC); `metrics` is a comma-separated list of `count` (the default), `sum(field)`, `avg(field)`, `min(field)`, `max(field)` over a numeric field, up to 6; `limit` is the number of groups, 50 by default and 200 at most. Each group has `key` (null for rows with no value) and one value for each computation, ordered by `key`; `totals` is the same computations over every row; `truncated` is true when groups remain that were not returned. `sum`, `avg`, `min` and `max` skip empty values and are null when a group has no value at all, `count` counts rows, and `avg` is rounded to four decimal places. With no `groupBy` there is only `totals`. A field or a computation that the model does not allow is 400, and no part of the request becomes SQL; the query is cut after 10 seconds |
| `GET /api/v1/data/{model}/{entity}/quality` | Quality figures of the rows the caller may see (ADMIN: every row of the entity, and only counts are accepted), taking the same `filter.*` filters and `q` as the list and `staleDays` (1 to 3650, 90 by default): `measuredAt`, `sampleSize` and `metrics`; `completeness` gives for each field the number of records that have a value (`filled`), `missing` and `rate`, where an empty string and an empty list count as missing and `rate` is `null` when `sampleSize` is 0; `requiredWhen` gives for each field that declares `required_when` the number of records that satisfy the condition (`applicable`) and the number of those where it is still empty (`missing`); `constraints` gives for each field with choices, `min`, `max` or `pattern` the number of stored values that violate it (`violating`); `freshness` gives the oldest and the newest change time and the number of records unchanged for more than `staleDays` days, not counting records in a final status; a role that does not touch the entity and is not ADMIN gets 403; the query is cut after 10 seconds |
| `POST /api/v1/data/{model}/{entity}/{id}/actions/{action}` | An action of the workflow, taking optional `version`/`modelVersion`, and omitting them keeps the behavior of an old client; a wrong version returns 409, and a changed model has `data.reason=MODEL_VERSION_CHANGED`; the metadata lists the handling roles (`handlers`), the actions with `roles`, `require` and `when` (`{field, op, value}`, where `op` is `==`, `!=`, `<`, `<=`, `>` or `>=`, `value` is a number for a `number` field, and `null` when there is no condition), the first status and who may act; the metadata of an entity has `handlerActions`, the names of the actions that the role of the caller may perform, so a client shows only the valid buttons |
| `POST .../{id}/assign`, `GET .../{id}/handlers` | Assigning work takes the `version`/`modelVersion` condition and returns version errors like an action; the list of people it can be assigned to |
| `GET .../{id}/events` | The history stream of the record; the `detail` of an `updated` row is JSON `{"field": ["old", "new"]}` with string or `null` values, cut at 200 characters |
| `.../{id}/files` | Upload, list, get a download link with an expiry (`/{fileId}/link`) and remove attachments |
| `GET .../{id}/documents`, `GET .../{id}/documents/{name}` | The print templates of the record and which can be printed in the current status; the PDF of one template, for people who can read the record (409 `DOCUMENT_NOT_AVAILABLE` when the status does not allow printing) |
| `GET /api/v1/inbox` | The records waiting for the caller, across every model: overdue records first, then the most recently changed (`updatedAt`) first, so a record just created, submitted again or reopened sits at the top; `page`, `size` |
| `GET /api/v1/inbox/stream` | An event channel `text/event-stream` for a signed-in person: after a history row of a record has been written in any model, the channel sends the frame `event: changed` with the data `{}`, carrying no content and the same for everyone, so the client reads the inbox again; a comment line `: ping` every 20 seconds; the server closes the channel after 10 minutes so the client reconnects with a new token; one person holds at most 8 channels and opening another closes the oldest; 503 when the server has used up the number of channels it can serve; the channel is under the limit of 300 opens per minute per person |
| `GET /api/v1/events` | The history stream in exactly the form of the webhook, from after an `eventId` (`after`, `size`, `model`) (ADMIN) |
| `GET /api/v1/events/admin` | Applying, going back, resuming and abandoning a model, and account changes, in exactly the form of the message `admin.event`, from after an `eventId` (`after`, `size`, `model`); `eventId` counts on its own, not in the same sequence as `/events`; a row is written whether or not there is a webhook target (ADMIN) |
| `GET /api/v1/outbox`, `POST /api/v1/outbox/{id}/retry` | The outgoing messages by status (failed, waiting, sent) and retrying a message that has not been sent (ADMIN) |
| `GET /api/v1/people` | Find people for a `user` field, returning only the id and the display name: `q` finds up to 20 accounts by name, username or email (fewer than 2 characters returns an empty list), `ids` is up to 50 comma-separated ids and returns the accounts that really exist; any signed-in person may call it |
| `GET /api/v1/clients`, `POST /api/v1/clients`, `PUT /api/v1/clients/{name}`, `POST /api/v1/clients/{name}/secret`, `DELETE /api/v1/clients/{name}` | Outside applications: list, register (`name`, `model`, `role`), switch to another role of the same model (`role`, keeping the secret), issue a new secret and delete (ADMIN); registering creates a client `dxos-app-{name}` that holds exactly one role of one model, and the secret appears only in the answer of the registration and of the secret change, with `Cache-Control: no-store` |
| `GET /api/v1/projects`, `POST /api/v1/projects`, `PUT /api/v1/projects/{name}`, `DELETE /api/v1/projects/{name}` | A project groups models and outside applications to filter and see the reach of a change, and grants no permission and isolates nothing (ADMIN): the list with the `models` and `clients` of each project, create (`name`, `label`, `description`), change the label and the description, delete; deleting a project that still holds a model or an application returns 409 |
| `PUT /api/v1/models/{model}/project`, `PUT /api/v1/clients/{name}/project` | Put a model or an outside application into a project, with the body `{"project": "name"}`; `null` takes it out of the project; 404 when the project, the model or the application does not exist (ADMIN); `GET /models` and `GET /clients` return `project`, `null` when it is not classified, and `POST /clients` takes an optional `project` |
| `GET /api/v1/projects/mine` | The projects the signed-in account is a member of, with the level `MEMBER` or `ADMIN`, and `global` is true when the account is a system-wide ADMIN; any account may call it |
| `GET`, `PUT`, `DELETE /api/v1/projects/{name}/members/{userId}` | The members of a project: view, add or change the level (body `{"level": "MEMBER"\|"ADMIN"}`), remove. A system-wide ADMIN and the administrators of that project may call it; a project administrator adds and removes only the level `MEMBER`, and raising or lowering an administrator is for the ADMIN, otherwise 403; removing a member does not remove the roles already assigned |
| `GET /api/v1/users`, `/users/options`, `/users/{id}` | Find and view users, their roles by model and their units; the roles and units that can be assigned (ADMIN). The administrator of a project sees only the members of their own projects, the roles of the models in that project and no units; 403 when there is no scope at all |
| `PUT`, `DELETE /api/v1/users/{id}/roles/{model}/{role}`, `/units/{unit}` | Assign and remove the role of a model, and a unit (ADMIN). A project administrator assigns and removes the roles of the models in their own project for the members of that project; units and unclassified models are for the ADMIN only, and outside the scope it returns 403 |
| `POST /api/v1/users`, `PUT /{id}/enabled`, `POST /{id}/password` | Create a user with a temporary password, lock and unlock, reset a password (ADMIN only) |
| `GET /api/v1/audit-logs` | The log of refused accesses, errors, account changes and model applies; filter by `actor`, `action`, `targetType`, `targetId`, `outcome`, `from`, `to` (ADMIN) |
| `GET /assistant-api/v1/features` | Whether the service is switched on, with no sign-in needed |
| `GET /assistant-api/v1/openapi.json` | The OpenAPI of the assistant, a sign-in is needed |
| `GET /assistant-api/v1/me` | Whether the caller has linked the Core (`linked`), whether they are an ADMIN (`admin`) and the classifiers that were loaded (`model.classifiers`) |
| `POST /assistant-api/v1/me/core/link`, `GET /assistant-api/v1/oauth/callback` | Link with the Core through SSO: `POST` returns `data.url` to send the browser to, `callback` takes `code` and `state` and then redirects to the page `/assistant` |
| `DELETE /assistant-api/v1/me/core/link` | Unlink: revoke the refresh token in Keycloak, delete the stored token and cancel the pending suggestions; `revoked` says whether Keycloak confirmed it |
| `POST /assistant-api/v1/me/reviews` | Review from 1 to 25 records, with the body `{"items": [{"model", "entity", "id"}]}`, read-only and creating no suggestion. `data.items` has one result for each eligible task: `model`, `entity`, `id`, `task`, `field`, `current`, `suggested`, `evidence` (up to 3 phrases), `mismatch`, and `confidence` when there is a suggestion; when the classifier refuses, `suggested` is `null` and `mismatch` is `false`. `data.skipped` counts records with an error of their own (no permission, missing, rate-limited, timed out); a session error (not linked, link expired) makes the whole round return an error |
| `POST /assistant-api/v1/me/proposals` | Create a suggestion for one record, with the body `{"model", "entity", "id", "task"}`. `data.proposal.snapshot` has `field`, `previousValue`, `value`, `evidence` and `confidence`; when the classifier refuses, `data.insufficient` is `true` and `proposal` is `null`. 409 `ERR_CLASSIFIER_UNAVAILABLE` when the weights of the task are missing, 409 `ERR_CLASSIFIER_LABELS` when the choices of the output field differ from the label set |
| `GET /assistant-api/v1/me/proposals`, `/me/proposals/{id}` | The history (paged with `page` and `size` of at most 5) and the detail of the caller's own suggestions, while the caller can still read the record |
| `POST /assistant-api/v1/me/proposals/{id}/revise` | Change the value, with the body `{"value": "..."}`; it creates a new suggestion and invalidates the old one |
| `POST /assistant-api/v1/me/proposals/{id}/confirm`, `/cancel` | Confirm or cancel, with the body `{}`. A suggestion expires after 120 seconds. Confirming reads the record again and sends a one-field `PATCH` with `version` and `modelVersion` to the Core: if the record, the model, the task or the weights have changed, it is 409 `ERR_PROPOSAL_STALE`, and a value equal to the record's is 409 `ERR_PROPOSAL_NO_CHANGE`; on success it returns `coreCommitted`, `changed` and `record` |
